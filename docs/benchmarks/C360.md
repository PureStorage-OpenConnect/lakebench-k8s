# Customer 360 Pipeline Benchmark Specification

Workload version `c360-2.dev1` (as stamped in `experiment.workload.version`),
query set `qs8-32043638dbc4`, maintenance policy `m2-2026-09-26`.

Audience: engineers who run, reproduce or compare this benchmark, and
contributors who implement it on a new component. Every statement describes
what the code of this release does, and names the module that does it.
Python paths are relative to `src/lakebench/`; generator paths to
`datagen_rs/`. Figures labelled "recorded" carry the run that recorded them;
those runs' records are published under `uat/runs/`.

## 1. Purpose and scope

Customer 360 models a retail and e-commerce business that consolidates raw
customer interaction events (purchases, browsing, support contacts, logins,
abandoned carts) from several source systems into one cleaned, enriched
interaction table, and then into a daily executive dashboard. The pipeline is
a medallion flow: raw Parquet lands in object storage (bronze), is filtered,
cleaned and enriched row by row (silver), and is aggregated to one row per
calendar day (gold). A fixed set of eight analytical queries is then run
against silver and gold.

What it measures about an architecture (catalog x table format x pipeline
engine x query engine, on a known system):

- Batch mode: how long the architecture takes to turn a fixed raw corpus
  into queryable gold (time to value), the data volume and compute it used
  on the way, and how fast its query engine answers the query set (QpH).
- Continuous mode: how stale gold is while a finite corpus is trickled in at
  a fixed offered load (data freshness), the ingest rate bronze holds, and
  the query engine's QpH while the tables are being written.

What it does not claim:

- It is not a customer-data-platform product. The cleaning rules are a fixed
  synthetic workload, not a reference implementation of identity resolution
  or data quality (the silver cleaning is partial by design, see section 12).
- The query set is not a validated business analytics suite. Query results
  are checked for cross-engine equivalence and for row counts, not for
  business meaning.
- A figure bounded by a Lakebench-imposed cap (executor ceiling, trickle
  rate, maintenance budget) is not an infrastructure capability.
- Not every expected-result check gates. Sixteen of the 34 checks in
  section 5.2 (every invariant and reconcile check, and the overall average
  transaction value) fail the run when they fail or do not run; the other
  statistical and row-count checks are recorded only. A passing batch run
  on a cluster proves non-degenerate output and those 16 expected results
  (a `--local` or `--stage` run evaluates none of them) and, when
  compared, cross-run result equivalence. Continuous runs are not checked
  against expected results.

## 2. Data model

Tables are created by the stage scripts through Spark DataFrameWriterV2
(Iceberg) or the Delta write helpers; there is no separate DDL file for
Customer 360. Default table names come from `TableNamesConfig`
(`default.bronze_raw`, `silver.customer_interactions_enriched`,
`gold.customer_executive_dashboard`), prefixed at runtime with the pipeline
catalog.

|---|---|---|---|---|---|---|---|
| Landing Parquet `s3://<bronze>/customer/interactions/part-NNNNNN.parquet` | bronze (raw) | both | one row per interaction event | `id` = `row_id` (unique per file block) | none; one object per file id | 2,478,560 (derived from the sizing code: 160 files x 15,491 rows) | 24,770,109 (1,599 files x 15,491 from the sizing code; the same count is recorded on run `20260929-212900-5105a0`) |

Notes on cardinality evidence. Run `20260929-212900-5105a0` is a scale-10
batch run recorded under workload version `c360-1`, on generator image
`lb-datagen:034f998`. Its row counts hold, but it was recorded under
identity version 1 and workload version `c360-1`, and its corpus id names a
different image, so it is not comparable with any run of this
release and it cannot be a reference run. The `c360-2` bump changed gold-finalize's
strategy choice on repeat runs, not the row counts of a first run. Dirty-data injection rewrites `email_raw`, `phone_raw`,

Domain dimensions (`config/scale.py`): scale 1 = 100,000 customer ids,
scale 10 = 1,000,000; nominal bronze 10 GB per scale unit. The
`approx_rows` figure there (customers x 24) is guidance only; the row count
datagen writes comes from file sizing (section 3).

## 3. Data generation

**Generator identity.** The Rust generator in `datagen_rs/` (entry
`datagen_rs/entrypoint.py`, driver `customer360_main` in
`datagen_rs/src/bin/generate.rs`). Customer 360 has no `MODEL_VERSION` of its own
(`DATAGEN_MODEL_VERSIONS["customer360"] = None`); its identity is the
generator image. Corpus id v1 hashes the configured image reference. Corpus
id v2 binds the image's lineage: the image digest that wrote the corpus,
mapped to the root of its output-neutral re-pin chain in
`src/lakebench/config/datagen_lineage.yaml` (`declared:<tag>` when no digest
was observed), so a re-pin with byte-compare evidence keeps the id and any
other image change moves it (`metrics/corpus_identity.py`). Default image:
`docker.io/sillidata/lb-datagen:a592385`
(sha256:48e18a417bf85528392afeb9b8222bfd3cc1d5f3db3bf1d7d0623e6a4f6ea4b1), whose lineage row maps it to the 1.6.0 image
(sha256:5fda9025fb9b455b390e1138d82e9f6ef16d214dfa9419815be0111d2f6fce0a), so
the two images give one lineage.

**Seed policy.** `datagen.seed` when set; otherwise 42. Any non-negative
seed is accepted for Customer 360; the AML spent-seed and registered-look
guards do not apply, and `corpus_role` is refused for this schema. The seed
drives two streams: the per-customer loyalty lookup (`Rng::new(seed)`) and
one RNG per file (`Rng::new(seed + file_id)`).

**Scale to dimensions.**

| Quantity | Formula (code) | Scale 1 | Scale 10 |
|---|---|---|---|
| Customer id space | `max(1, round(scale x 100,000))`, or `customer360.unique_customers` | 100,000 | 1,000,000 |
| Target bytes | `approx_bronze_gb / 1024` TB, rendered to 6 decimals | 0.009766 TB | 0.097656 TB |
| Files | `max(1, target_bytes // file_size)` | 160 | 1,599 |
| Rows per file | `max(1000, file_size / bytes_per_row)`, bytes_per_row 4,332 (snappy, default) | 15,491 | 15,491 |
| Rows | files x rows per file | 2,478,560 | 24,770,109 |

`bytes_per_row` is codec-conditional (`DG_COMPRESSION`: zstd 2,233, lz4
4,356, none 4,399); nothing in the Lakebench config or Job template sets
`DG_COMPRESSION`, so snappy applies unless the Job is edited by hand. The
payload size is fixed at 2 KiB. Files are assigned to pods by
`file_id % total_nodes`; a file's content depends only on the seed, file
id, rows per file, customer id space, dirty ratio and timestamp window, so
pod count does not change the corpus. The file size is fixed at 64 MB;
`datagen.file_size` refuses any other value.

**Row model.** Rows are generated in sessions of 5 to 20 rows; each session
has one customer, one `session_id`, a timestamp anchor drawn uniformly in the
window, and rows within 30 minutes of it. Customer ids come from a truncated
Zipf sampler: the 500 lowest ids receive 40% of sessions with Zipf(1.2)
weights, the rest uniform over the remaining ids (ids are 1-based). Interaction
type weights: purchase 0.18, browse 0.35, support 0.12, login 0.20,
abandoned_cart 0.15. Purchase amounts are `clamp(exp(N(4.3, 1.2)), 1,
9999.99)` rounded to cents; every other row has 0.0. Page views are 1 to 20 on
purchase and browse, else 0; time on site 30 to 3,629 s when page views > 0.
Support rows carry a ticket, issue and satisfaction 1 to 5; all others are
NULL. Login and support rows have NULL `product_id`, `product_category`,
`click_count` and `items_in_cart`, and NaN `cart_value`; store
and call_center rows have NULL device and browser. 60% of customer ids are
loyalty members (tiers 70/20/10), fixed per id for the run. 40% of rows carry
a campaign. `data_source` weights 0.70/0.15/0.10/0.05 and `data_quality_flag`
weights clean 0.92, duplicate_suspected 0.02, incomplete_data 0.03,
format_inconsistent 0.03 are drawn per row, independently of dirty
injection.

**Dirty-data injection.** `dirty_data_ratio` (default
0.08, validated to [0, 1]) is the target aggregate share of rows selected
for corruption per field. The per-row probability is `ratio x
DIRTY_RATE_BY_SOURCE[source] / weighted_mean`, where the per-source shape is
primary_system 0.005, legacy_import 0.35, manual_entry 0.15, third_party_api
0.05 and the weighted mean is about 0.0735, clamped at 1.0. Four independent
Bernoulli passes select rows of `email_raw` (6 modes), `phone_raw` (4
modes), `city_raw` (10 misspellings) and `state_raw` (casing and
abbreviation variants). A selected email, phone or state is always
rewritten. A selected city is rewritten only when it has a misspelling: 8 of
the 22 city entries (San Antonio, San Diego, Dallas and San Jose, two
entries each) have none, and cities are drawn uniformly over the 22, so the
realised `city_raw` share is about 14/22 (0.64) of the ratio. The selection
share equals the ratio for ratios up to about 0.21; above that
legacy_import saturates and the aggregate falls short (0.5 gives about 29%).
Independently, 10% of emails carry a `.DUPLICATE` marker
(`duplicate_email_pct`, fixed, not configurable from Lakebench).

**Time range.** `event_timestamp` is drawn in `[timestamp_start,
timestamp_end)`, dates in `YYYY-MM-DD`. Single-cycle default: 2024-01-01 to
2025-01-01 (366 days) from the Rust binary when the config sets neither.
Multi-cycle default: 2024-01-01 to 2025-12-31 (730 days), split into
`cycles` equal slices (the last takes the remainder).

**Multi-cycle windows.** With `pipeline.cycles = N > 1` (batch only), the
CLI runs one datagen Job per cycle before that cycle's stages, unless
`--skip-generate` reuses a finished multi-cycle corpus of the same config
(checked against the corpus series marker, below); `run --generate`,
`run --generate-only` and `generate` on a multi-cycle config are refused
(exit 2), because a whole corpus generated first would be read again by
cycle 0 (section 4.1). The windows are `config/c360_run.py`
`cycle_windows`. Cycle n gets
its time slice, `target_tb / N`, and `--cycle n --cycles N`; for n > 0 the
file id handed to the row generator is `fid + (n << 32)`, giving disjoint RNG
streams and row ids, and objects are named `part-cNNN-NNNNNN.parquet`. The
customer id space and loyalty lookup are the same in every cycle. A
multi-cycle corpus is not the same corpus as a single-cycle one at the same
seed and scale.

**Delivery modes and byte identity.** `datagen.mode` selects the S3
delivery pattern: `batch` (one PUT per file), `continuous` (S3 multipart as
row groups close), `auto` = `continuous`; the entrypoint forwards the
configured mode to the generator. Row content is byte-identical across
delivery modes at a fixed seed (Rust row-identity tests). Delivery mode is
independent of pipeline mode.

**Fresh generate.** A batch `run --generate` or a `generate` over a bronze
datagen prefix (`customer/interactions/`) that holds any object is refused
(exit 3). On a bucket this deployment can prove it owns, `--regenerate`
deletes that prefix (aborting incomplete uploads; never the rest of the
bucket) and `--skip-generate` reuses the data when its corpus series marker
matches the config (below); on a bucket it cannot prove
it owns, only `--allow-stale-bronze` proceeds, writing over the objects and
recording that. The CLI refuses with exit 4 when it cannot read the bucket
to check. Inside datagen, before cycle 0 writes, the prefix is cleared again
on an owned bucket; on any other bucket a non-empty prefix stops datagen
unless `--allow-stale-bronze` was given (`deploy/datagen.py`,
`cli/_helpers.py`). Before the gate, an earlier datagen Job is deleted; if
its pods are still running five minutes later the command refuses (exit 3),
and if they cannot be listed it exits 4. `--regenerate` applies only with
`--generate` or `--generate-only` and is refused on a local run and on a
continuous run other than `--generate-only`; `--allow-stale-bronze` applies
only to a run that generates into bronze (`--generate`, `--generate-only`
or a multi-cycle batch run). Both refusals exit 2 (`cli/_run_args.py`).

Continuous runs other than `--generate-only` do not go through the CLI
gate: their preflight clears raw data unless `--skip-generate` (section
4.2). If objects land in the prefix
after that reset on a bucket this deployment cannot prove it owns, datagen
refuses to start (exit 3); `--allow-stale-bronze` does not apply to a
continuous run other than `--generate-only`.

**Corpus series marker.** Every generate writes
`customer/interactions/_corpus/series.json` (`deploy/corpus.py`): the cycle
count, the cycles whose datagen Job finished, each cycle's window, the
generation parameters (seed, scale, customer id space, file size, target size
per cycle, dirty ratio, image, window bounds) and the image digest the
datagen pods ran. It is written unfinished when the generate starts and
completed cycle by cycle; every clear of the prefix first writes a marker
saying a clear is under way and keeps it. A batch run that reuses bronze
(`--skip-generate`, or one cycle without `--generate`) is refused (exit 3,
`run.series_mismatch`) when the marker is unfinished or names another cycle
count, window or generation than the config's; a single-cycle run over a
corpus with no marker (1.6) proceeds, unless the prefix holds later-cycle
files. No stage reads `_corpus/`.

## 4. Pipeline

Stage scripts: unsuffixed files are the Iceberg adapters, `*_delta.py` the
Delta adapters; `bronze_verify.py` serves both formats. Every Spark session
is pinned to UTC before any date is derived.

### 4.1 Batch mode (`pipeline.mode: batch`)

`lakebench run` runs the stages below in order, each as one
SparkApplication; a failed stage stops the run. In a single-cycle run
datagen runs first only with `--generate`. With `cycles > 1`, datagen runs
before every cycle unless `--skip-generate` reuses a finished multi-cycle
corpus, and `--generate` is refused before any cluster call (exit 2,
`cli/_run_args.py:RUN_RULES`).

1. **bronze-verify.** Input: every landing Parquet file of this run's cycles.
   Transformation: none (no bronze table is written in batch). Checks:
   23 required columns present with the right type families, 9 pass-through
   columns (warn only), row count > 0, at least one row surviving the silver
   filter, and no key column (`event_timestamp`, `customer_id`,
   `interaction_type`, `channel`, `data_quality_flag`) NULL in every row. A
   key column that is NULL in only some rows is logged as a warning. Any
   failure exits 1. Outputs: the `[c360-bronze] rows=N silver_filter_rows=M`
   fact line, and `max(event_timestamp) + 1 day` written to the
   `lakebench-silver-state` ConfigMap as the bronze data clock.
2. **silver-build.** Input: the same landing files (cycle-scoped globs in a
   multi-cycle run). Transformation: drop rows flagged
   `duplicate_suspected` (NULL flags are dropped too), then the 32 derived
   columns of 2.2, with `customer_recency_score` anchored to the data clock
   `LB_DATA_CLOCK` (in a multi-cycle run, every cycle takes the exclusive
   end of the range its cycles cover, `data_clock_source` `cycle_series_end`;
   otherwise the resolution order is `timestamp_end`, bronze-verify's
   ConfigMap value, `timestamp_start`, today at 00:00 UTC; the day before the
   value is the anchor). Strategy: `simple` below 100 GB of bronze,
   `streaming` at or above (single pass, hash distribution by partition);
   `salted` is refused. Output: silver, created with `createOrReplace` on
   cycle 0 (an existing table whose columns differ, such as one a
   continuous run wrote, is first dropped from the catalog; its files stay
   in the bucket) and appended on later cycles after deleting that cycle's
   `_batch_id` rows. Invariants enforced: refuses a full rebuild over a
   populated silver table unless `--force-rebuild`; refuses when the data
   clock is unset; fails when rows written is 0 or cannot be read from the
   snapshot summary.
3. **gold-finalize.** Input: the whole silver table. Transformation: group
   by `interaction_date` with the 30 KPIs. Strategy: `simple_agg` below 500
   GB of silver, `two_phase_agg` above; cycles 2+ force `incremental`
   (recompute from the latest gold date inclusive and rewrite gold in one
   commit). Output: gold, `createOrReplace`, coalesced to one file. Exits 1
   when silver is missing or empty. Then the non-degeneracy gate: the stage
   counts gold rows and the distinct silver
   `interaction_date` values (two full reads) and exits 1 when they differ,
   on Iceberg and Delta and under every strategy. Then it logs the
   `[c360-check]` fact line (one silver aggregation pass and a gold
   collect, reporting only); only that check's own seconds are subtracted
   from the stage's time, so the gate's reads count toward the stage and
   time to value (section 8.1).
4. **Pre-benchmark maintenance and benchmark** (section 7.2 and 6): an
   optional pre-maintenance benchmark round, table maintenance, a storage
   settle wait, and the scored benchmark round with result fingerprints.

### 4.2 Continuous mode (`pipeline.mode: continuous` or `run --continuous`)

1. **Preflight.** Resolve the trickle (`max_files_per_trigger`) and the
   maintenance schedule; refuse the run when data would stop arriving before
   the window ends, when an explicit maintenance or compaction interval
   cannot fire inside the window, or when `run_duration < 3 x
   gold_refresh_interval`. Refuse to drop existing Customer 360 state
   (tables, checkpoints, or raw data larger than this run regenerates)
   without `--force-reset`. Stop leftover streams, delete stream
   checkpoints, and clear raw data unless `--skip-generate`.
2. **Datagen** starts (whole corpus, finite) and runs concurrently.
3. **Continuous reset.** bronze-verify with `LB_CONTINUOUS_RESET=1` drops
   `bronze_raw`, silver and gold and their owned directories; it verifies
   nothing and writes no data clock.
4. **Three concurrent streams**, each a SparkApplication:
   - **bronze-ingest**: Structured Streaming file source over the landing
     prefix, `maxFilesPerTrigger` files per `bronze_trigger_interval`
     (default 30 s), appended to `bronze_raw` exactly once per micro-batch
     (Iceberg snapshot properties or Delta txnAppId/txnVersion). Waits up to
     1,800 s for the first file. Refuses a fresh checkpoint over a non-empty
     table.
   - **silver-stream**: incremental read of `bronze_raw`, the same silver
     transformation as batch per micro-batch every `silver_trigger_interval`
     (default 60 s), exactly-once append keyed by (`_stream_id`,
     `_batch_id`). Waits up to `silver_bronze_wait_seconds` (default
     `run_duration / 4`, at least 10 s) for bronze to appear.
     Refuses resume when bronze's snapshot lineage changed under its
     checkpoint. Fails at stop when it wrote 0 rows.
   - **gold-refresh**: a rate source used as a timer every
     `gold_refresh_interval` (default 5 minutes); each cycle re-aggregates
     the whole silver table with the same 30 KPIs and replaces gold, then
     logs data freshness (section 8.2). Five consecutive silver read errors
     fail the stream. The batch non-degeneracy gate does not run here.
5. **Measurement window.** Opens when every stream's driver is RUNNING and
   closes `run_duration` seconds later (default 1,800). Inside it:
   in-stream benchmark rounds (section 6) and table maintenance rounds
   (section 7.2).
6. **Gates** (section 5.3), then **settle and result check**. The CLI
   estimates how long the rest of the corpus needs to reach gold (remaining
   rows at the rate bronze held, plus two silver triggers, two gold
   refreshes and 60 s). When that estimate exceeds 1,800 s the result check
   is skipped outright, with no wait, and the run records
   `results.not_checked`. Otherwise it keeps the streams running until every
   datagen row is in bronze, silver has committed all of them and a gold
   refresh has read silver after its last commit, stops the streams, runs
   the query set once and fingerprints every result. None of this is scored.

## 5. Correctness contract

### 5.1 Checks that gate a run (fail it)

| Check | Mode | Where |
|---|---|---|
| Unsupported workload x architecture x mode, or a scale above the workload's datagen ceiling (600 for Customer 360), refused before anything runs (exit 2) | both | `cli/_run.py`, `config/support.py` |
| Prerequisites (cluster capacity included), infrastructure readiness, and a Spark Operator that is not ready or not watching the namespace refused (exit 4); a missing namespace exits 5 unless `--yes` deploys it first | both | `cli/_run.py` |
| A dependency set that is missing or stale (exit 4) or does not match the deployment (exit 3) refused before anything is recorded | both | `cli/_helpers.py` |
| At run end, a query engine pod that ran a different dependency set, jobs built on a different set than the one recorded, or pods that could not be read for the check, fail the run and the verdict's `dependency_set` gate (skipped after an interrupt or a prerequisite failure) | both | `cli/_helpers.py`, `metrics/verdict.py` |
| `run --generate` or `generate` over a non-empty bronze datagen prefix refused (exit 3) unless `--regenerate`, `--skip-generate` or `--allow-stale-bronze` applies (section 3); an unreadable bronze bucket exits 4 | batch | `cli/_helpers.py`, `deploy/datagen.py` |
| Datagen exceeds its wait: the run exits 1 after deleting the datagen Job and any stream apps, and the verdict's reasons say datagen timed out; a failed datagen in any cycle of a multi-cycle run fails the run | batch | `cli/_run.py` |
| bronze-verify: schema, a key column NULL in every row, rows > 0, rows surviving the filter > 0 | batch | `bronze_verify.py` |
| silver-build: rows written > 0, known row count, data clock set, no unintended full rebuild | batch | `silver_build*.py` |
| gold-finalize: silver exists and is non-empty | batch | `gold_finalize*.py` |
| gold-finalize: gold row count equals the distinct silver `interaction_date` count (Iceberg and Delta, every strategy) | batch | `gold_finalize*.py`, `common.py` |
| Any stage exit code other than success | both | `cli/_run.py`, `cli/_sustained.py` |

### 5.2 Expected-result checks (batch only)

After gold-finalize the CLI evaluates 26 pipeline checks from the
`[c360-bronze]` and `[c360-check]` facts, and after the benchmark 8 query
row-count checks (`benchmark_rows_Q1` and so on), into `metrics.json`
`c360_correctness`. The record's status is `fail` when any check failed;
otherwise `pass` when the five core checks ran and passed, else `unknown`.
Continuous runs, `--local` runs and `--stage` runs do not evaluate them, so
their verdict carries no `c360` gate.

Sixteen checks gate the run (`GATING_CHECKS` in
`metrics/c360_correctness.py`): every invariant and reconcile check below
and `avg_transaction_value_overall`. A gated check that fails, does not
run, or is absent from the record, and a record with no expected-result
facts, fail the run: it exits non-zero, `metrics.success` is false, and the
verdict's `c360` gate fails, so the report shows the run as failed and
the perf gate refuses it. The other 18 checks (the remaining
statistical checks and the benchmark row counts) are recorded and printed
only: a failure among them is listed under the verdict's
`c360_failed_not_gating` qualifier and changes neither the exit code nor
the verdict.

Check ids, by kind: invariant `silver_duplicate_filter_applied`,
`amount_only_on_purchases`, `purchase_amount_range`, `silver_no_null_keys`,
`customer_ids_in_id_space`, `dates_in_window`,
`one_ticket_and_score_per_support`, `gold_counts_non_negative`,
`gold_daily_identities`, `daily_active_within_customers`; reconcile
`bronze_rows_match_datagen`, `bronze_to_silver_rows`,
`silver_to_gold_days`, `silver_to_gold_counts`, `silver_to_gold_revenue`;
statistical `duplicate_filter_share`, `interaction_mix`,
`avg_transaction_value_overall` (gated), `avg_transaction_value_daily`,
`avg_page_views_per_visit`, `avg_time_on_site_per_visit`,
`avg_satisfaction_score`, `high_churn_share`, `medium_churn_share`,
`distinct_customers`, `gold_days_cover_window`; shape `benchmark_rows_Q1`,
`benchmark_rows_Q2`, `benchmark_rows_Q3`, `benchmark_rows_Q4`,
`benchmark_rows_Q5`, `benchmark_rows_Q6`, `benchmark_rows_Q7`,
`benchmark_rows_Q9`.

| Kind | Checks (tolerance) |
|---|---|
| invariant (exact) | no `duplicate_suspected` row in silver; amount > 0 only on purchases and transactions = purchases; purchase amount in [1, 9999.99]; no NULL customer, date or amount; customer ids in [1, id space]; dates in [window start, window end - 1 day]; ticket rows = support rows = satisfaction rows; gold counts never negative or NULL; per-day gold identities (avg transaction value = revenue / transactions within 0.011, avg estimated LTV = total LTV / transactions within 0.011, both averages NULL exactly on days with no transactions, transactions = conversions, tickets = support, channel revenue <= total, churn <= support, largest transaction in range, LTV >= revenue); max daily active customers <= id space |

### 5.3 Continuous window gate

A continuous run fails unless, inside the window: bronze ingested rows,
wrote at least 2 batches, and wrote its last batch at or after 50% of the
window (a corpus drained before the window opened fails explicitly); silver
committed at least 2 micro-batches with rows after bronze's first write in
the window; gold refreshed on new silver data at least 2 times after that
write (a cycle tagged `(silver idle)`, reading no silver, or reading no more
silver rows than the previous cycle does not count); gold freshness was
measured; and every stream's driver log has timestamped stage lines.

### 5.4 Result equivalence

Batch: after the timed samples of the scored round, each successful query is
run once more, untimed, and its result fingerprinted (spec `rf2`:
order-independent row hashes, approximate DOUBLE-derived columns compared as
plain and row-weighted sums within a tolerance scaled from each column's
declared quantum and the row count, timestamps normalised to UTC;
`benchmark/fingerprint.py`). Continuous: the fingerprints of the post-settle
result check. In-stream rounds and the pre-maintenance round are never
fingerprinted.

Fingerprints are compared only between runs of the same corpus. Two runs
are not comparable when they were recorded with different
identity versions, when their corpus id differs (corpus id v2 on exp2
records; corpus id and generator image on exp1 records), when their seed,
scale or corpus role differs, or when their generator image digests differ
where both runs observed one (`metrics/comparability.py`). A tester
therefore produces a fresh reference run on the same generator image and
seed before comparing.

## 6. Query set

`query_set_id` is `qs8-32043638dbc4` in this release: `qs<count>-` plus the
first 12 hex characters of a SHA-256 over each distinct query name and its
registry SQL text, sorted by name (a name not in the registry hashes by
name only). The hash covers the registry SQL, not engine-rewritten SQL.
Changing any query's SQL changes the id, and QpH across ids is refused. A
batch run's id is computed from every query name in the result, successful
or not. A continuous in-stream round records the set of queries that
succeeded in it, and the post-settle result check hashes every query it ran
(section 8.2). Execution order in a power run: Q1, Q2, Q4, Q3,
Q7, Q5, Q6, Q9. There is no Q8.

| Id | Business question | Reads | Rows on a correct corpus (checked in 5.2) |
|---|---|---|---|
| `Q1_full_aggregation_scan` | How many interactions, customers and sessions, total revenue, and the mean transaction value? | silver | 1 |
| `Q2_filtered_aggregation` | For each day of the first three months of data and each interaction type: interactions, customers, revenue | silver | 5 x days in the first 3 months |
| `Q4_churn_risk_analysis` | Where are high and medium churn-risk interactions, by journey stage and device category, among segments with more than 10 customers? | silver | 6 (2 risks x retention x 3 device categories) |
| `Q3_customer_segmentation` | For transacting rows, customers, spend, engagement and estimated LTV per value tier and channel preference | silver | 12 (3 tiers x 4 preferences) |
| `Q7_channel_conversion_funnel` | Per channel: funnel counts, conversion rate, revenue, engagement | silver | 5 |
| `Q5_revenue_trend_ma7` | Daily active customers and revenue with 7-day moving averages, latest 90 days | silver | min(90, days) |
| `Q6_customer_rfm` | How many customers fall in each RFM segment, with average spend, frequency and recency, as of the newest date in the data? | silver | 1 to 6 |
| `Q9_executive_dashboard` | Latest 30 days of the dashboard with day-over-day revenue and DAU change | gold | min(30, days) |

The expected row counts are the ones the `benchmark_rows_*` checks require
(`metrics/c360_correctness.py:benchmark_checks`), with the conditions given
in section 5.2.

**Tie-breaking.** Every `ORDER BY` that feeds a `LIMIT` or window ends in a
unique key: Q5 and Q9 order by `interaction_date`, which is unique per row of
their input. Queries without a `LIMIT` (Q2, Q3, Q4, Q6, Q7) may return rows
in engine-dependent order among ties; the fingerprint is order-independent,
so this does not affect equivalence.

**Time zone.** Stage sessions are pinned to UTC; query sessions are pinned
to UTC on every engine (Trino `--timezone`, Spark Thrift
`spark.sql.session.timeZone=UTC`, DuckDB `SET TimeZone='UTC'`); a timestamp
without a zone is fingerprinted as UTC.

**Dialect.** Queries are written in Trino dialect; engine adapters rewrite
dialect and, on DuckDB, table references, nothing else (for example `date_add('month', 3, x)` to `add_months(x, 3)` and
`DATE_DIFF('day', a, b)` to `DATEDIFF(b, a)` on Spark Thrift). Q6 computes
recency from `MAX(interaction_date)` in the data, not the run date, so its
result is a function of the corpus.

## 7. Execution rules

### 7.1 Required

- Batch: all three stages in order (`--stage` runs one stage and skips the
  correctness evaluation, so it is not a benchmark run), then the benchmark
  unless the recipe has no query engine.
- Continuous: all three streams for the full window, the gates, and the
  result check; a run without the result check (`--skip-benchmark`, no query
  engine, corpus did not settle or was too large to settle within 1,800 s)
  cannot be shown comparable.
- Iterations: batch timed samples per query = `benchmark.iterations`
  (default 3, range 1 to 100), scored by the per-query median; continuous
  in-stream rounds take 1 sample per query whatever the config says; the
  result check takes 1.
- Per-stage timeout: `--timeout`, else `max(3600, scale x 120)` seconds.
  Benchmark query timeout 300 s. The phase-3 datagen wait uses the same
  timeout; exceeding it deletes the datagen Job and the stream apps and
  exits 1. Datagen wait in a multi-cycle run: the same timeout per cycle,
  and a cycle that exceeds it fails the run. Stream start deadline 1,800 s.
- A repeat batch run on the same deployment needs `--force-rebuild` (silver
  refuses to overwrite a populated table otherwise). With `--generate` it
  also needs `--regenerate`, which deletes only the datagen prefix, and
  only in a bronze bucket this deployment can prove it owns. On any other
  bucket `--regenerate` is refused, and `--allow-stale-bronze` generates
  over the existing objects and records that it did. Use `--skip-generate`
  instead to reuse the existing corpus.

### 7.2 Maintenance policy handling

Maintenance is an execution condition. The policy id is
`m2-2026-09-26`; `--skip-maintenance` stamps `m2-2026-09-26+skipped`. The
effective maintenance (what ran, per operation) is recorded in
`experiment.effective_maintenance` with classes `ran`, `ran_no_effect`,
`not_supported`, `skipped_by_user`, `failed`, `not_run`.

| Composition | Batch pre-benchmark | Continuous in-window |
|---|---|---|
| Iceberg + Trino | expire_snapshots at 0 s and remove_orphan_files at 24 h 10 min on silver and gold; compaction on silver and gold as `ALTER TABLE ... EXECUTE optimize(file_size_threshold => '128MB')`, split into statements of at most 90 `interaction_date` partitions each when silver holds more | expire at max(retention_threshold, 1 h) and orphan removal at 24 h 10 min on bronze_raw, silver, gold every `retention_interval` (auto `run_duration / 3`, 300 to 7,200 s); the same compaction statement on silver and gold every `compaction_interval` (auto 2 x retention) |
| Iceberg + Spark Thrift | expire and orphan removal as for Trino; compaction as `CALL <catalog>.system.rewrite_data_files(table => ...)` with Iceberg's default file selection | as for Trino, with the Thrift compaction statement |
| Delta + Trino | VACUUM at the resolved retention; OPTIMIZE never runs (`not_supported`) | VACUUM at Delta's 7-day default while streams are live (`ran_no_effect`); no OPTIMIZE. Delta continuous has no effective maintenance, and the record says so in `known_limitations` |
| Delta + Spark Thrift | VACUUM and OPTIMIZE skipped (`not_supported`) | same (`not_supported`) |
| DuckDB (Iceberg) | no maintenance (`not_supported`); the settle wait is skipped because no statement ran | no maintenance (`not_supported`) |
| No query engine | no benchmark, no maintenance | no rounds, no result check, no maintenance |

Both Iceberg compaction statements aim at the table's 128 MB
`write.target-file-size-bytes`, but they select files differently. The
record names the operation (`compaction=ran(trino_optimize:128MB)` against
`compaction=ran(iceberg_rewrite_data_files)`), and the compaction operation
is a Conditions key, so a Trino-vs-Thrift pair that both compacted is not
like-for-like (`metrics/maintenance_policy.py`, section 10).

Batch sequence (when a query engine exists and neither `--skip-benchmark`
nor `--skip-maintenance` nor `pre_benchmark_maintenance: false` applies):
file count probe; a pre-maintenance round (warm-up pass, then timed, not
fingerprinted) at scale below 50 only; maintenance and compaction under one
1,800 s budget (the first statement timeout or the deadline stops the rest,
and the run records `maintenance_stopped`); query-engine readiness wait;
**storage settle wait**: probe one scan query every 60 s until two
consecutive probes agree within 10% and neither is slower than the
pre-maintenance median by more than that bound, which widens to the probe
query's own spread (twice its median absolute deviation, at most 20%) when
the pre round timed it three or more times; with no pre-maintenance time
(scale 50 and above) the wait needs three agreeing probes and is recorded
as unverified. Three failed probes in a row end the wait. It waits at most 2,700 s (configurable in
`benchmark.maintenance_settle`; `benchmark/settle.py`); then the scored
round. The scored round is preceded by a warm-up pass only when a
pre-maintenance round was measured; at scale 50 and above, with
`--skip-maintenance`, or with `pre_benchmark_maintenance: false` it starts
cold.
The settle wait is outside every stage and outside time to value. A wait
that does not settle leaves `maintenance_value_pct` null. When stream apps
are present or cannot be read in the namespace, batch pre-benchmark
maintenance switches to live-stream retention and records that it did.

Continuous statements get `min(600 s, interval / 2)` each, and a round is
skipped when too little window is left. When the configured engine's pod is
missing, maintenance falls back to the other engine; when tables or rounds
then compacted with different statements, the record names both as
`mixed(...)`. Batch Customer 360 has no bronze
table, so batch maintenance never targets `bronze_raw`.

### 7.3 Permitted tuning (still publishable)

None of these changes the Workload or Corpus keys of the experiment
identity, so runs that differ only here stay comparable. What the
difference means depends on the setting. A different component or version
is an Architecture difference and a different cluster a System difference
(with both at once, no difference can be put down to either); the
conditions of section 10 and the dependency pinset make a pair not
like-for-like. Explicit Spark executor overrides, driver overrides and user
Spark conf are Architecture keys when set, and an executor override below
the profile's ask also enters as the bound kind `*: executor override`, a
condition. Other sizing and execution settings are not in the experiment
identity at all: two runs that differ only in Trino, Thrift or DuckDB
sizing, storage classes, datagen execution, or continuous trigger
intervals carry equal identities, unless a larger `gold_refresh_interval`
raises the floor of the benchmark warmup and interval and so changes the
in-stream round count (a condition). The perf gate fingerprints those
settings and refuses a run whose settings differ from its pinned config
(`metrics/perf_gate.py`). State them beside any published comparison:

- Architecture choice among the supported compositions (section 11) and
  component versions within `_SUPPORTED_SPARK_VERSIONS` (3.5, 4.0, 4.1) and
  `_FORMAT_VERSION_COMPAT`. Spark 3.5 is accepted (Iceberg only; Delta needs
  Spark 4.x) but is in no release-matrix row, so its runs are unverified.
- System sizing: Spark per-job executor counts
  (`platform.compute.spark.*_executors`), driver cores and memory, Spark
  conf overrides, query-engine sizing (Trino workers and memory, Thrift,
  DuckDB), storage classes. Per-executor profiles are fixed by
  `_JOB_PROFILES` and not configurable.
- Datagen execution: `parallelism`, `cpu`, `memory`, `generators`,
  `datagen.mode` (delivery pattern: `batch` puts each file in one PUT,
  `continuous` streams S3 multipart, `auto` resolves to continuous).
- Continuous: trigger intervals, `max_files_per_trigger` (within the
  arrival rule; an explicit value has no upper bound; in no identity key,
  so a difference leaves the identities equal), maintenance intervals and retention
  threshold (the Conditions key "maintenance settings", so a difference
  is not like-for-like), benchmark warmup and interval (both floored at
  `gold_refresh_interval`) and `run_duration`. A change to the last three
  is not like-for-like when it changes the in-stream round count (a
  condition) or, for `run_duration`, the auto maintenance intervals derived
  from it.
- Batch: `benchmark.iterations`, `pre_benchmark_maintenance`,
  `maintenance_settle`, `--skip-maintenance`. Iterations and the effective
  maintenance are Conditions keys (a difference is not like-for-like);
  `maintenance_settle` is not recorded in the identity.

### 7.4 Prohibited changes (invalidate a result or are refused)

Refused before the run: a scale above the datagen ceiling (at deploy,
generate and run, section 11). Refused at config load or run start: an unsupported
composition
(`_SUPPORTED_COMBINATIONS`, `WORKLOAD_TABLE_FORMATS`, `WORKLOAD_MODES`);
`schema: custom`; Spark 4.2; `corpus_role` or `robustness_perturbation` on
Customer 360; `cycles > 1` with continuous mode; an explicit
`max_files_per_trigger` that offers the corpus before the window ends; an
explicit maintenance or compaction interval that cannot fire in the window;
`run_duration < 3 x gold_refresh_interval`. `spark.lb.silver.strategy=salted`
is refused by the silver-build job when it starts, so the stage fails;
likewise `spark.lb.gold.strategy=incremental`, or a value that names no
strategy, is refused by gold-finalize when it starts.

Make two runs not comparable: records
of different identity versions (exp1 against exp2), a record missing a
required identity key or with its seed withheld, a run that did not pass (a
failed verdict, including a failed gating `c360_correctness` check), a
different workload, workload version,
workload parameters id, mode, query set, corpus id, seed, scale, corpus
role or cycle count above 1, a different generator image (exp1 records) or
generator digest (compared only when both runs recorded one), a mixed or
disagreeing datagen fleet, or any differing result fingerprint. On an exp2 record the corpus id is v2: the hash of the
generator's own resolved arguments, model version, image lineage and cycle
count. On an exp1 record it is the config hash of schema, generator image,
seed, corpus role, perturbation, scale, timestamp window,
`dirty_data_ratio` and `unique_customers` (`metrics/experiment.py`,
`metrics/corpus_identity.py`). A record is exp2 only when the generator
wrote its per-node corpus markers (`_corpus/` in the bronze scope), the run
started under identity version 2, and (on a cluster run) part of the
system identity was observed from the cluster; otherwise it is exp1 and lists what was missing
in `experiment.v2_unavailable`.

`datagen.file_size` is fixed at `64mb`, so it cannot move the corpus. The
codec (`DG_COMPRESSION`) changes every file's rows but is reachable only by
editing the datagen Job by hand; an exp1 corpus id does not see it, so do
not publish a comparison across such an edit. Editing stage scripts or the
KPI list without bumping `WORKLOAD_VERSIONS` would compare under the same
version; bump it. Nothing detects a stage-script or KPI change without a
bump: the tests pin only the current value.

| `sustained_throughput_rps` | rows/s | higher | bronze rows written by batches that started inside the window / `arrival_seconds`. When `intake_limit` is `trickle_rate` it is the configured offered load (a Lakebench cap), not a capacity |
| `window_seconds` | s | none | the measured window length; follows the configured `run_duration` |
| `arrival_seconds` | s | none | whole window while corpus remained; else bronze's last write inside the window plus one bronze trigger |
| `window_arrival_fraction` | ratio | none | `arrival_seconds / window_seconds` |
| `pre_window_rows` | rows | none | bronze rows before the window; in no window score |
| `released_rows` | rows | none | rows the trickle had made available to bronze by the window's end: files per trigger x triggers since bronze's first write, at the corpus mean rows per file, capped at the corpus |
| `ingest_ratio` | ratio | target, guard | bronze rows by the window's end / `released_rows`; falls back to `corpus_ingest_ratio`. A guard: the run should sit inside 0.95 to 1.05 |
| `corpus_ingest_ratio` | ratio | none | bronze rows / datagen rows; below 1 on a default run, whose trickle is sized to outlast the window |
| `pipeline_saturated` | bool | none | `ingest_ratio < 0.95`; when `intake_limit` is `trickle_rate`, whether silver failed to keep pace (null when silver's pace is unmeasured) |
| `intake_limit` | text | none | `none`, `trickle_rate`, `bronze_capacity` (bronze busy >= 80% of the window), `below_bronze_capacity`; can be null |
| `bronze_busy_fraction` | ratio | none | share of the window bronze spent inside micro-batches |
| `corpus_drain_seconds` | s | none | datagen rows / rows per second when intake was trickle-bound |
| `corpus_drained` | bool | none | every datagen row in bronze and committed by silver before the window closed |
| `stage_latency_profile` | struct | none | mean micro-batch time per stream (`bronze_ms`, `silver_ms`, `gold_ms`) |
| `total_rows_processed` | rows | none | rows taken in inside the window across streams (gold re-reads of silver included) |
| `composite_qph`, `in_stream_composite_qph` | QpH | higher | median QpH over in-stream rounds with QpH > 0; rounds run every `benchmark_interval` after `benchmark_warmup` (both at least `gold_refresh_interval`), 1 sample per query, Q9 retried twice after 30 s and 60 s. A round's QpH is over the queries that succeeded in it; after a successful Q9 retry it is recomputed over every query in the round, failed ones included |
| `composite_qph_rounds`, `benchmark_rounds_count` | count | none | rounds behind the median, and rounds executed |
| `composite_qph_basis`, `composite_qph_by_set` | struct | none | whether the median blends rounds that executed different query sets, the rounds per executed set, and the median per set |
| `qph_degradation_pct` | pct | lower | `(1 - median(second half) / median(first half)) x 100`, 4 or more rounds |
| `qph_degradation_withheld` | text | none | why `qph_degradation_pct` is absent with 4 or more rounds: the rounds ran different query sets |
| `query_time_event_age_seconds` | s | none | median age of gold's newest event date at query time; tracks the corpus's position in time, not freshness |
| `total_elapsed_seconds` | s | none | wall clock of the whole run, from run start (before datagen and stream submission) to the record, including stream start-up, the result check and its settle wait; shared with batch in name only |
| `pipeline_throughput_gb_per_second`, `compute_efficiency_gb_per_core_hour` | GB/s, GB/core-h | higher | `total_data_processed_gb` (stream input sizes, falling back to measured bucket sizes, plus the query stage's gold size when rounds ran) over the window; efficiency is the streams' input over their core-hours |
| `total_s3_objects` | count | none | objects across the three buckets at the window's end, before the settle wait; unbounded growth means maintenance is not keeping up. Batch records do not carry it |
| `total_core_hours` | core-h | none | core-hours of the streams, which scale with the window (config-bound) |

Each in-stream round records the query set it executed: a round with a
tolerated Q9 failure executed a 7-query set (`qs7-...`). When the rounds
behind the median executed different sets, `query_set_id` reads `blended`,
`composite_qph_basis.blended` is true, `composite_qph_by_set` gives the
median per set, and the median is not comparable with another run's. A published
continuous `composite_qph` must carry `composite_qph_basis`.

## 9. Disclosure requirements

`metrics.json` carries an `experiment` block: schema `exp2` (identity
version 2) when corpus id v2, the identity version and an observed system
identity exist, otherwise `exp1`, with `v2_unavailable` naming what was
missing (`metrics/experiment.py`). A published result must carry all of it:

- workload name `customer360` and version `c360-2.dev1`; parameters id and the
  resolved `unique_customers` and event window;
- corpus: id, generator image as configured and as run, digest, seed,
  scale, timestamps, `dirty_data_ratio`, whether each was observed from
  the datagen pods or only declared, and, on exp2, corpus id v2 and its
  lineage; problems when the pods disagree;
- architecture: recipe, catalog, table format and query engine types and
  versions (Hive as the derived Stackable image), Spark image, query access
  path (`catalog`, `direct_storage`, or null when the recipe has no query
  engine);
- system (`cluster` or `local`), support state frozen at run start
  (`supported`, `unverified`, `unsupported`) and its basis;
- mode; maintenance policy id, configured maintenance settings and
  effective maintenance per operation (including the compaction
  operation), with known limitations;
- stages executed and skipped (a skipped benchmark or maintenance is
  listed);
- limits: benchmark iterations and mode, continuous rounds and trickle,
  executor caps with `cap_hit` and budget caps, auto-sizing cuts,
  maintenance stop, the bound kinds;
- results: `query_set_id` and one fingerprint per query, or
  `not_checked` with the reason; for continuous `composite_qph`, its
  `composite_qph_basis`;
- the `c360_correctness` record: its 16 gating checks drive the verdict and
  the exit code, and other failures are reported only (5.2);
- repetitions: runs = 1 and samples per query; a repeatability claim needs
  repeated runs or an `n=1` label;
- the Lakebench provenance (commit, dirty tree flag).

## 10. Comparability

Lakebench does not compare runs for you; a reader compares two reports (see
[Comparing Runs](../benchmarking.md#comparing-runs)). For C360, two runs are
comparable only when all of these hold (`metrics/comparability.py`):

- both passed (FAILED, INTERRUPTED and VOID runs have no performance to
  compare; a failed gating `c360_correctness` check fails the verdict), and
  both carry an experiment block of the same identity version;
- every Workload and Corpus identity key (7.4) is equal, and neither run has
  a corpus problem;
- they ran the same query set and every result fingerprint matches.

A run with no checked results (`--skip-benchmark`, a `*-none` recipe, a
continuous run that did not settle or skipped the result check) cannot show
it returned the same answers. The execution conditions are the effective
maintenance, the compaction operation, the maintenance settings, the
benchmark iterations and mode, the Lakebench limits that bound, and
(continuous) the in-stream round count; when they differ, or only the
dependency pinset does, a difference in the numbers may come from them. The
query access path and the system are Architecture and System keys, not
conditions; when the architecture and the system both differ, no difference
can be put down to either. Because the compaction operation is a condition,
a Trino-vs-Thrift Iceberg pair that both compacted differs in conditions
(7.2).

The perf gate and `reproduce` require every identity key, conditions
included (except the in-stream round count), to match their stored
reference, and refuse a different maintenance policy id. Compare QpH only
between runs with the same non-unknown `query_set_id`; a continuous median
over rounds that executed different sets reads `blended` (8.2). The perf
gate and `reproduce` leave out continuous rows per second when the corpus
drained with less than 90% arrival.

## 12. Known limitations

- **Proven on one system type.** Live runs so far are on OpenShift with
  Portworx scratch and FlashBlade S3; the minimum cluster is what
  `lakebench plan` reports.
- **Supported tuples outside the release matrix are unverified.** Spark 3.5
  is accepted but is in no release-matrix row, so its runs are unverified.
- **Settings outside the experiment identity.** Runs that differ only in
  query-engine sizing, storage classes, datagen execution, or continuous
  trigger intervals carry equal identities (7.3), unless the change moves
  the in-stream round count; only the perf gate refuses them. State these
  settings beside any published comparison.
- **Only 16 of the 34 expected-result checks gate the run.** The 16 in
  `GATING_CHECKS` fail the run and its exit code when they fail or do not
  run; the other 18 are reported only. A statistical check at 6 standard
  errors can fail a correct run by chance (the module puts that probability
  well under 1e-6 per check). Continuous runs have no expected-result
  checks; their correctness rests on the window gate and on fingerprint
  equality with a reference run.
- **Continuous QpH can be over a smaller query set.** A failed Q9 is
  tolerated in in-stream rounds; rounds that executed different sets give
  `query_set_id: blended`, are not assessed, and `composite_qph_basis`
  records the rounds per set.
- **Multi-cycle regenerates every cycle**: with `cycles > 1`, datagen runs
  before every cycle even with `--skip-generate`, so a multi-cycle run
  cannot reuse an existing corpus; `--generate` is refused on it. Before
  cycle 0 the run clears the datagen prefix in a bronze bucket this
  deployment can prove it owns. In any other bucket, existing objects are
  refused unless `--allow-stale-bronze` is passed; cycle 0 then reads them
  as this run's data and can over-count rows.
- **Lakebench names no winner.** Comparing two runs is left to the reader
  (section 10).
- **Delta continuous has no effective maintenance**: small files accumulate
  and in-window QpH can decline, so its composite QpH is not a steady-state
  figure. Delta batch never runs OPTIMIZE, and on Spark Thrift runs no
  VACUUM either.
- **DuckDB runs no maintenance** and reads storage directly. A DuckDB run
  differs from a Trino or Thrift run in access path (Architecture) and
  effective maintenance (a condition); two runs that both used
  `--skip-maintenance` have the same effective maintenance.
- **Continuous throughput is an offered load bounded by the trickle.** The
  derived (auto) trickle is at most 50 files per 30 s trigger; an explicit
  `max_files_per_trigger` has no upper bound, subject only to the arrival
  rule. At large scales the default window offers only part of the corpus
  and the run reports `intake_limit: trickle_rate`; rows per second under
  that cap is the offered load, not a capacity.
- **Large continuous corpora may not settle.** When, at the end of the
  window, the rest of the corpus would need more than 1,800 s to reach gold
  at the ingest rate bronze held (plus two silver triggers, two gold
  refreshes and a minute), the result check is skipped without waiting, the run records `results.not_checked`, and
  it cannot show it returned the same answers as another run.
- **Executor ceiling.** Executor counts do not grow up to scale 10, and stop
  at the per-job cap above it (28 for silver-build and gold-finalize, 20
  for bronze-verify and silver-stream, 10 for bronze-ingest and
  gold-refresh); time to value at those points is bounded by the profile,
  and the record marks the job with `cap_hit` under `limits.executors`.
- **Pre-maintenance round only below scale 50**, so `maintenance_value_pct`
  is absent at scale 50 and above, and the settle wait is unverified there.
- **Silver cleaning is partial.** State standardisation maps only CA, TX, NY
  and FL spellings, and city standardisation only New York, NYC and LA; the
  Illinois, Arizona and Pennsylvania variants and the misspelled cities the
  generator injects pass through. Email cleaning only lowercases,
  trims and removes the `.duplicate` marker. No query reads these columns, so query results are
  unaffected; gold `unique_emails` does depend on `email_clean`.
- **`silver_processing_timestamp` and, in continuous runs,
  `customer_recency_score` depend on when the run happened.** A continuous
  run without `timestamp_end` resolves its data clock from a bronze
  ConfigMap value left by an earlier batch run, when no generate gate or
  destroy cleared it, then from `timestamp_start` if set, and only then from
  today (the continuous reset writes no data clock), while batch anchors it
  to the corpus's last day. No query reads either column.
- **Multi-cycle time to value includes later cycles' datagen**; `cycles`
  above 1 is a Corpus identity key, and the perf gate refuses multi-cycle
  runs.
- **Stage timing** comes from pod and API-server clocks mapped to the host
  clock; stages that fall back to the 5 s status poll are labelled
  `timing_source: poll`.
- **Repeatability.** A single run is `n=1`; a repeatability claim needs
  `run --repeat` or repeated runs.
