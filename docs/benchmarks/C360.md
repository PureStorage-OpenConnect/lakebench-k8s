## 1. Purpose and scope

Customer 360 models a retail and e-commerce business. It consolidates raw
customer interaction events (purchases, browsing, support contacts, logins,
abandoned carts) from several source systems. The result is one cleaned,
enriched interaction table, then a daily executive dashboard. The medallion
flow:

- bronze: raw Parquet lands in object storage;
- silver: filtered, cleaned and enriched row by row;
- gold: aggregated to one row per calendar day.

Eight analytical queries then run against silver and gold.

What it measures about an architecture (catalog x table format x pipeline
engine x query engine, on a known system):

| Mode | Measures |
|---|---|
| Batch | time to turn a fixed raw corpus into queryable gold (time to value); data volume and compute used; query-set speed (QpH) |
| Continuous | gold staleness while datagen writes at the scale's offered load (data freshness); the ingest rate bronze holds; QpH while tables are written |

What it does not claim:

- It is not a customer-data-platform product. The cleaning rules are a fixed
  synthetic workload, not a reference implementation of identity resolution
  or data quality. Silver cleaning is partial by design
  ([12](c360/limitations.md#12-known-limitations)).
- The query set is not a validated analytics suite. Results are checked for
  cross-engine equivalence and row counts, not business meaning.
- A figure bounded by a Lakebench cap (executor ceiling, continuous
  [trickle](../glossary.md#trickle), maintenance budget) is not an infrastructure
  capability.
- Not every expected-result check gates
  ([5.2](c360/correctness.md#52-expected-result-checks-batch-only)):
  - 16 of the 34 fail the run and its exit code when they fail or do not run;
  - the other 18 statistical and row-count checks are recorded only.
- A passing cluster batch run proves non-degenerate output and those 16
  expected results. When compared, it also proves cross-run result
  equivalence. A `--local` or `--stage` run evaluates none of the checks.
- Continuous runs are not checked against expected results.

## 11. Supported compositions

Customer 360 is declared for Iceberg and Delta, batch and continuous, within
its datagen scale band (`config/support.py:DATAGEN_SCALE_BANDS`):

- above 600 is unsupported and refused at deploy, generate and run (exit 2);
- above 300 up to 600 is unverified and warned.

Support states per recipe and mode are in the generated
[support table](../compatibility-matrix.md#support-states). Customer 360 is
supported only on the cells it lists; every other valid combination is
unverified.

| Recipe | Access path | Notes |
|---|---|---|
| hive-iceberg-spark-trino (default) | catalog | |
| hive-iceberg-spark-thrift | catalog | query and pipeline share Spark |
| hive-iceberg-spark-duckdb | direct_storage | no maintenance |
| hive-iceberg-spark-none | null (no query engine) | no benchmark, no result check |
| polaris-iceberg-spark-trino | catalog | |
| polaris-iceberg-spark-thrift | catalog | |
| polaris-iceberg-spark-duckdb | direct_storage | no maintenance |
| polaris-iceberg-spark-none | null | as hive-iceberg-spark-none |
| hive-delta-spark-trino | catalog | no OPTIMIZE; continuous has no effective maintenance |
| hive-delta-spark-thrift | catalog | no VACUUM, no OPTIMIZE |
| hive-delta-spark-none | null | as hive-iceberg-spark-none |
| local (hadoop catalog + DuckDB, `--local`) | direct_storage | batch unverified, continuous unsupported; Customer 360 batch only; always queries with DuckDB, whatever the recipe names; runs no expected-result checks |

Refused at load ([Compatibility Matrix](../compatibility-matrix.md#excluded-combinations)):

- Delta + DuckDB (delta-kernel ignores S3 endpoint settings);
- Polaris + Delta (Iceberg-only catalog);
- any Unity composition (none is in `_SUPPORTED_COMBINATIONS`);
- Spark 4.2;
- `custom`.
