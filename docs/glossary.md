# Glossary

Reference: terms used in Lakebench reports, records and docs.

| Term | Meaning | Defined in |
|---|---|---|
| <a id="look"></a>Look, registered look | One scoring of a held-out AML corpus under the pre-registration. Each held-out seed gets exactly one registered look, on one datagen image named by digest. | [AML spec 3.3](benchmarks/aml/seed-policy.md#33-seed-policy) |
| <a id="held-out"></a>Held-out | An AML evaluation or robustness seed. The repository stores only its salted hash, and Lakebench refuses its corpus outside a registered look. | [AML spec 3.3](benchmarks/aml/seed-policy.md#33-seed-policy) |
| <a id="in-sample"></a>Seed 43, in-sample | The AML calibration corpus, and the seed an unset `workload.datagen.seed` resolves to. The generator, rule thresholds and reference features were developed on it, so its figures are in-sample. | [Reading AML results](aml-scoring.md#held-out-evaluation) |
| <a id="level-2"></a>Level-2 | The claim that calibrated difficulty replicates out of sample: the evaluation corpus's per-typology average precision falls in intervals predicted from the calibration runs. The robustness corpus is compared with the same intervals, but that comparison is not a replication test. No Level-2 result is published. | [Reading AML results](aml-scoring.md#held-out-evaluation) |
| <a id="tick"></a>Tick | One AML gold-refresh detection pass in a continuous run. Every continuous rule (W2, W3, W4, W5, W6, W17) runs every tick; W1, W7 and W8 are recorded as `mode-excluded`. | [AML spec 4.3](benchmarks/aml/pipeline.md#43-continuous-mode) |
| <a id="drain"></a>Drain | How a continuous run ends. Intake stops at window end and the stages finish the rows already taken; AML gold-refresh finishes its tick, then stops. | [Result check](benchmarking/verdict.md#result-check), [AML spec 4.5](benchmarks/aml/pipeline.md#45-continuous-drain-and-tick-records) |
| <a id="covered"></a>Covered scoring, covered instance | A covered instance is a planted instance the last tick could have detected: every participant payment and entity was in sealed silver. `recall_covered` is the designated-rule hit rate over them, never the batch `recall`. | [Continuous recall](aml-scoring.md#continuous-recall-over-covered-instances) |
| <a id="trickle"></a>Trickle | A per-trigger limit on bronze intake: `max_files_per_trigger` files per trigger. It is a Lakebench cap. `intake_limit: trickle_rate` records that it bounded intake, so throughput is the rate the trickle released (`released_rows`), not a capacity. | [Trickle-bound throughput](benchmarking/continuous.md#trickle-bound-throughput) |
| <a id="intake-limit"></a>Intake limit | The `intake_limit` field: why `ingest_ratio` is under 0.95 (`trickle_rate`, `bronze_capacity`, `below_bronze_capacity`), or `none`. | [Intake limits](benchmarking/continuous.md#intake-limits) |
| <a id="offered-load"></a>Offered load | The rate datagen writes files in a continuous run, set by scale: AML 4 MB/s and Customer 360 10 MB/s per scale unit. | [Offered load and regimes](benchmarking/continuous.md#offered-load-and-regimes) |
| <a id="capacity-run"></a>Capacity run, steady-state run | Capacity (`datagen_ahead: true`, `intake_limit: bronze_capacity`): datagen outran bronze, so the paces are the pipeline's capacity. Steady state (`datagen_ahead: false`): the pipeline kept up, so freshness is the score and paces are the arrival rate. | [Offered load and regimes](benchmarking/continuous.md#offered-load-and-regimes) |
| <a id="balance"></a>Balance check, bottleneck | The continuous gate fails a run whose stage lag rose by more than one cadence across the window's second half. The bottleneck is the stage that fell behind, named in `continuous.balance`. | [Continuous gate](benchmarking/verdict.md#continuous-gate) |
| <a id="settle"></a>Settle | Batch: the storage settle wait after maintenance. Settled means two consecutive probes agree within `tolerance_pct` and neither is slower than the pre-maintenance median by more; with no pre round (scale 50 and above), three consecutive probes must agree (`maintenance_settled`). Continuous: the drain's finish, within the 1800 s settle limit, before the result check. | [Storage settle wait](benchmarking/maintenance.md#storage-settle-wait), [Result check](benchmarking/verdict.md#result-check) |
| <a id="caps"></a>Lakebench caps (binding) | Limits Lakebench imposes: executor caps, budgets, the trickle, benchmark iterations. `experiment.limits` lists the caps a run executed under; `limits.bound` the binding ones, which bounded it. A number measured under a binding cap is a property of the cap, not the infrastructure. | [Lakebench caps](benchmarking/maintenance.md#lakebench-caps) |
| <a id="support-states"></a>Support states | `supported`: the release validation record lists the workload x recipe x mode at the run's Spark minor and table format version, Lakebench runs from an unmodified tree, and the scale is inside the supported band. `unverified`: valid but not validated. `unsupported`: refused before a run. | [Support states](compatibility-matrix.md#support-states) |
| <a id="corpus-id"></a>Corpus id | The identity of a generated corpus: generator, seed and scale. Version 2 binds the image lineage that wrote it. | [Comparing runs](benchmarking/comparing.md), [C360 generation](benchmarks/c360/generation.md) |
| <a id="query-set-id"></a>Query set id | `query_set_id`: the queries a run's benchmark ran. Changing a query changes it, and QpH across ids is refused. | [In-stream QpH basis](benchmarking/query-benchmark.md#in-stream-qph-basis) |
| <a id="result-fingerprint"></a>Result fingerprint | A per-query fingerprint of the answer, from one untimed execution. A fingerprint that failed matches nothing. Runs with different fingerprints are not comparable. | [Comparing runs](benchmarking/comparing.md) |
| <a id="time-to-detect"></a>Time to detect | AML continuous: the commit of an alert's rule INSERT into `gold.alerts` minus the newest bronze `ingest_ts` among its related payments (`time_to_detect_seconds`). | [AML spec 8.2](benchmarks/aml/continuous-metrics.md#82-continuous) |
| <a id="freshness"></a>Freshness | `data_freshness_seconds`: the maximum, inside the window, of each gold refresh's age of its newest row, from file landing. The primary continuous score. | [Freshness](benchmarking/continuous.md#freshness) |
| <a id="qph"></a>QpH | Queries per hour: `(num_queries / total_seconds) * 3600` in power mode. `composite_qph` is `sqrt(power_qph * throughput_qph)`. | [Query benchmark](benchmarking/query-benchmark.md#modes) |
