# Datagen and pipeline live observability (Pushgateway)

Maintainer material. Describes the Pushgateway path as shipped in v1.6.

Datagen pods and the Spark pipeline stages are batch jobs that can finish
inside one Prometheus scrape interval, and the Spark PrometheusServlet is off
(`spark.ui.enabled=false`, the driver-OOM fix), so Prometheus pull
alone gives no live signal for them. Each deployment therefore runs a
Prometheus Pushgateway that those jobs push to. The Pushgateway is a
best-effort live view only. `metrics.json`, built from the stdout and stderr
metric lines, remains the single authoritative artifact for every published
number (DESIGN.md invariant 5); nothing is published off the dashboard.

## Only when monitoring is requested

The Pushgateway deploys only when the config sets `observability.enabled:
true` (default false) and `observability.pushgateway_enabled` (default true).
With `observability.enabled` off, `ObservabilityDeployer.deploy()` returns
SKIPPED; with only `pushgateway_enabled` off, the stack deploys without the
Pushgateway templates. With either off there is no gateway, `LB_PUSHGATEWAY_URL` is not injected, every pusher
no-ops, and metrics still land in `metrics.json`.

Config (`config/schema.py` `ObservabilityConfig`):

| Field | Default |
|---|---|
| `pushgateway_enabled` | `true` |
| `pushgateway_image` | `prom/pushgateway:v1.11.1` |
| `pushgateway_storage` | `1Gi` |
| `pushgateway_storage_class` | `px-csi-scratch` |

## Ownership

Per deployment (ownership category 1). `templates/pushgateway/pushgateway.yaml.j2`
renders a PVC, a Deployment and a Service `lakebench-pushgateway` in the
deployment namespace; `destroy` removes them with the namespace. The gateway
runs with `--persistence.file` on the PVC (`--persistence.interval=30s`) so a
pod restart does not drop a completed stage's final push before Prometheus
scrapes it. Its container requests 100m CPU and 128Mi and is limited to 1 CPU
and 512Mi.

The shared kube-prometheus-stack Prometheus in `lakebench-observability`
scrapes it through `templates/pushgateway/podmonitor-pushgateway.yaml.j2`,
rendered into the deployment namespace. The PodMonitor carries `release:
lakebench-observability`, which the shared `podMonitorSelector` already
matches, so no shared category-4 state is mutated. It sets `honorLabels:
true`, so the pushed `job` and `run_id` labels survive the scrape instead of
becoming `exported_*`.

Service URL: `http://lakebench-pushgateway.<namespace>.svc:9091`, injected as
`LB_PUSHGATEWAY_URL` (with `LB_RUN_ID`) into the datagen Job
(`deploy/datagen.py`, `templates/datagen/job.yaml.j2`) and the Spark driver
env (`modules/pipeline_engines/spark/job.py`).

## Push mechanics

Every push is an HTTP `PUT` to `/metrics/job/<job>/<label>/<value>...`, which
replaces the whole group. Pushes are best-effort: a 2 s timeout, no retry, and
any error is swallowed.

- **Emit then push.** The authoritative log line (`LB_METRICS_JSON` on
  datagen stderr, the `JOB METRICS` block on the Spark driver) is written
  first, so a push failure can never lose it.
- **Datagen** (`datagen_rs/src/push.rs`, `metrics.rs`): a dependency-free
  HTTP/1.1 request over `std::net::TcpStream` (no hyper; the crate hand-builds
  its output). A reporter thread pushes in-progress rows, bytes, elapsed
  seconds and throughput about every 10 s; it reads only atomics, so it cannot
  perturb generated bytes. The final push after generation replaces those
  partials with the full per-pod set.
- **Spark** (`spark/scripts/common.py` `_push_stage_metrics`, called from
  `log_job_metrics` on the driver only): stdlib `urllib` on a daemon thread,
  so a slow or unresolvable gateway cannot stall a streaming trigger. Only
  stages that report through `log_job_metrics` push, once at completion:
  AML bronze-verify, silver-build and gold-finalize, and Customer 360
  gold-finalize (Iceberg and Delta). Customer 360 bronze-verify and
  silver-build write their metrics block directly and do not push. In
  continuous mode only the AML silver-stream side blocks (statements and KYC
  refresh) push; no Customer 360 continuous stage does.

## Metric contract

`namespace` comes from the scrape target. Grouping labels identify the rest.

### Datagen

Grouping labels: `job="datagen"`, `node_id`, `schema`, `run_id`.

- `lakebench_datagen_rows_written`, `lakebench_datagen_bytes_written`,
  `lakebench_datagen_files_written` (gauges, per pod, safe to sum)
- `lakebench_datagen_throughput_mbps` (gauge). Bounded by the Lakebench-set
  pod resources (CPU as configured, default 8; auto-sized memory from the
  datagen memory model, capped at 16Gi per pod; a `datagen.memory` you set is
  used as given), so the dashboard labels it as capped
  (invariant 6).
- `lakebench_datagen_elapsed_seconds`, `lakebench_datagen_cpu_seconds`
- `lakebench_datagen_phase_seconds{phase=...}`: setup, world, typology, gen,
  reference, build_batch, encode_parquet, s3_put (phases a schema does not
  run are omitted)
- `lakebench_datagen_corpus_total_txns`: a corpus-wide constant, pushed under
  its own group (`job="datagen_corpus"`, `schema`, `run_id`, no `node_id`) so
  it is one series and a `sum()` cannot multiply it by the pod count.

The periodic push carries only rows, bytes, elapsed and throughput; files,
CPU seconds and phases arrive with the final push. There is no
`_total_files` series.

### Spark stages

Grouping labels: `job="spark_stage"`, `stage`, `run_id`.

- `lakebench_stage_input_rows`, `lakebench_stage_output_rows`,
  `lakebench_stage_input_size_gb`, `lakebench_stage_elapsed_seconds` (gauges)
- `lakebench_silver_table_rows{table=...}`: one series per `silver_<table>_rows`
  key the stage logs

Batch-stage series are completion-only final totals; panels never apply
`rate()` or `increase()` to them.

## Grafana

The Lakebench Overview dashboard (`templates/grafana/dashboard-configmap.yaml.j2`)
is rendered once into `lakebench-observability`, not per namespace
(a fixed uid rendered per namespace collided in the shared Grafana). It is
applied idempotently on every deploy and left in place by `destroy`.
Template variables `namespace` and `run_id` come from `label_values(...)` on
`lakebench_stage_elapsed_seconds`. Every Pushgateway panel filters on
`namespace=~"$namespace", run_id=~"$run_id"`; the Trino and node CPU panels
filter on `namespace` only.

Panels: datagen throughput MB/s (cap-labelled), datagen rows written by pod,
datagen phase seconds (stacked), bronze/silver stage rows (input vs output),
silver per-table row counts, pipeline stage elapsed seconds, Trino running
queries, Trino query throughput, node CPU usage by pod.

## Known limitations

- **Stale groups persist.** Nothing issues a DELETE: groups stay in the
  gateway, and in its persistence file, until the deployment is destroyed.
  The `run_id` label and dashboard variable keep a viewer on one run, but an
  earlier run's groups remain selectable, and a query without a `run_id`
  filter sees them.
- **No retry.** A push that fails is lost; the next periodic push or the
  final push supersedes it, and `metrics.json` is unaffected.
- **Selectors need a stage push.** The `namespace` and `run_id` variables
  are populated from `lakebench_stage_elapsed_seconds`. A run with no
  finished pushing stage (only generated data, or a Customer 360 continuous
  run, which pushes no stage series) does not appear, and a deployment whose
  runs never push a stage cannot be selected even for its Trino and CPU
  panels.
- **Customer 360 stage panels are partial.** Customer 360 bronze-verify and
  silver-build do not push, so on Customer 360 the stage rows panel shows
  only gold-finalize and the silver per-table panel is empty.
